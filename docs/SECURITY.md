# Security model and release gate

The default Phase 1 mode contains local development fixtures only and initializes no provider client. Its PIN and preferences are separate from connected-account state. Local setup requires PIN confirmation and cannot overwrite an existing verifier through the setup route; changing it requires the current PIN. In connected mode, Supabase Auth establishes an account session; a separate device PIN opens the private UI. Every cold start begins locked after initial setup. Pending PIN/biometric results are invalidated by relocking, backgrounding or controller disposal, so late verification cannot reopen a locked screen. Routes and notification intents must pass both gates. Auth recovery requires an email/password reauthentication before replacing the device PIN; possessing an old persistent session is not sufficient. Losing the device verifier does not recover an account password.

New device PINs contain 4–8 digits. Previously stored longer verifiers remain accepted for compatibility. The secure storage record contains a random 256-bit salt and a PBKDF2-HMAC-SHA256 verifier (600,000 iterations), never the PIN. Starting at five failures, persisted exponential backoff limits attempts to once per 30 seconds, increasing to one hour. Secure storage failures fail closed. This is a device UI gate, not a defense against a rooted device, a compromised OS, offline attacks on extracted verifiers, or an already stolen backend session. A numeric PIN has limited entropy; choose a long random PIN and a strong account password.

Android FLAG_SECURE masks previews and blocks screen capture for the entire activity. This must be confirmed on target OEM devices. Calculator branding does not hide the application from system settings, permissions, network traffic, or foreground-service notifications.

Private buckets use membership checks and short-lived signed links. Signed links are bearer capabilities until expiry; do not share or log them. RLS and TLS are not end-to-end encryption. Database administrators and authorized infrastructure can read messages and media. LiveKit transport encryption is not an E2EE claim. No custom end-to-end cryptography is implemented.

Call token issuance rechecks both participants' current membership, blocks, state and expiry on the server. Acceptance also checks membership and blocks. A previously issued LiveKit JWT remains a bearer capability until its initial 90-second expiry; adding a block does not instantly revoke an already issued token or disconnect established media. Terminal room closure runs through the scheduled worker and depends on successful provider access. Verify revocation timing and cancellation on real devices before release.

Release requires deployed migrations, security tests against the deployed project, verified provider configuration, a release signing key, and the physical-device checklist in TESTING.md. Unit and widget tests cannot establish notification delivery or real device calling behavior.

Build inputs are allowlisted by `scripts/prepare-client-config.py`. Privileged Supabase JWTs/secret keys, arbitrary fields and test passwords are rejected before CI packaging. Firebase native resources are generated from matching public Android console identifiers and ignored by Git. Server configuration belongs exclusively in Supabase secrets. The APK inspection script checks signatures/metadata and known private-key formats; it cannot certify the absence of every possible encoded secret or replace code review.

Foreground/background FCM payload construction uses generic Calculator/New activity text with PRIVATE visibility and opaque routing IDs only. Foreground routing drops any sender/text/image fields and requires the matching authenticated owner and local PIN gate. Registration callbacks are scoped to a registration generation/account; unregister cancels callbacks and attempts local cleanup even after a failed server deletion. Offline stale-token rows may remain until provider/retention cleanup; generic payloads and RLS still apply. Real notification delivery/privacy in Android OS states remains unverified.

Deployment must target an owner-confirmed staging project with remote schema and migration history reviewed before applying changes. `supabase/remote_preflight.sql` is read-only metadata inspection. Hosted tests require explicit target/write consent and disposable accounts; their configuration must never be used as Flutter build input. No provider deployments or real-device security validation occurred in this phase.

## Phase 3 changes and limits

Presence callbacks, session startup and repository channels/timers are account/lifecycle guarded. Online publication follows last-seen privacy. Outbox retries retain UUIDs, distinguish transient errors and bound in-flight waits. Downloads enforce declared sizes before retaining bytes; forwarding requires a fresh destination-owned, server-validated upload. PostgreSQL tests cover cross-conversation path denial and destination-only access. Audio/recorder operations avoid starting after disposal; native plugin behavior still needs hardware verification.

Terminal call updates retry under their original account while the controller lives. They are not a durable process-death queue: losing the process or signing out can leave server state until existing scheduled cleanup (accepted calls have a two-hour cap) and LiveKit room closure. Do not claim instant remote termination during outages. New location declarations authorize only foreground one-time sharing; Bluetooth permission is requested explicitly for audio routing. Native compilation and OEM permission/background behavior remain unverified.

See the [Phase 3 evidence and remaining release blockers](PHASE3_BETA_READINESS.md). Local tests are not an independent penetration test, hosted RLS certification, malware scanner, performance benchmark or E2EE implementation.

## Phase 4 — implemented controls and disabled E2EE

Read [PHASE4_SECURITY.md](PHASE4_SECURITY.md) and [ENCRYPTION_DESIGN.md](ENCRYPTION_DESIGN.md). The official native Signal probe is verified only in its test scope; direct/group messages and media remain readable by authorized infrastructure. There is no production encrypted transport, key-directory/backup implementation, identity-verification UI or E2EE claim for LiveKit.

New additive migrations enforce message expiration before cleanup, tombstones against stale retry resurrection, single service-side view-once claims and ordinary Storage denial. Worker cleanup is eventual; existing signed URLs/external copies/backups can outlive application access. View-once cannot prevent another camera or a modified recipient from retaining content.

Optional device approval adds restrictive table/Storage/Realtime policies, guards definer RPCs and Edge Functions, binds push registrations to signed JWT session IDs and filters revoked registrations. Enabling it requires a coordinated deployment and a retained approved device. This is account-access security, not cryptographic device authentication; revocation does not erase offline copies or instantly evict existing LiveKit streams/capabilities. Password-confirmed actions use an isolated verification session. Hosted verification and a reviewed lost-approved-device recovery procedure remain required before broad rollout.

Repository suspension releases plaintext/cache-key references after pending operations settle. Known-expired content is pruned from encrypted caches/outboxes, media renderers close on expiry/relock, and private viewer files/cache entries are removed best effort. Dart/native/GPU/flash erasure is not guaranteed. Keep provider/runtime logs free of passwords, tokens, message bodies, decryption keys and signed media URLs.

## Phase 5 call authorization and privacy

Calling source now uses server-owned invitation states, accepted-session binding and per-join media epochs. A room token requires current conversation membership, no applicable blocks, joined state, device authorization and a live accepted call; voice/video grants are separately source-scoped, 90 seconds, without room administration/recording/data grants. Genuine SQL/concurrent-transaction and signed test-JWT tests pass; actual provider admission/eviction does not.

Host/admin removal, group leave/end and revocation queue epoch-specific LiveKit cleanup. Signed media join/leave webhooks supply reconnect-grace evidence; old events cannot overwrite a newer join. Current clients recheck authorization during active calls. Existing media/refresh behavior, worker timing and previously issued capabilities require real-provider validation; no instant erase/revoke guarantee is made. Multi-device ringing is disabled by selecting one authorized registration per invitation.

Incoming payloads/actions contain opaque routing metadata and an expiry, no names/previews. No background handler obtains media tokens or starts capture; notification actions pass Auth/device/PIN gates. Capture FGS readiness precedes publication, projection uses explicit system consent and stops on lock/end. The projection prompt's scoped inactive exception never suppresses actual background/manual/inactivity locking. FLAG_SECURE and Android mandatory notifications/indicators are retained. Telecom, PiP and full-screen-intent exemptions are not implemented. [Full threat/OS limits and verified scope](PHASE5_CALLS.md).

Calls use WebRTC transport encryption; neither calls nor existing messages are represented as verified application E2EE. Phase 4 encryption integration/recovery blockers remain.

## Phase 6 release hardening

A reproduced local account/cache-boundary defect was fixed: delayed conversation/message reads and hide responses now revalidate their original account, exact cache instance and session epoch before mutation; invalidated initialization releases references. Cache clearing suspends channels/timers and invalidates old readers first. Four adversarial adapter/encrypted-file tests fail on the old code and pass after the fix. This is local isolation evidence, not hosted authentication or forensic memory erasure.

Release tasks reject absent/incomplete signing configuration. Protected manual CI requires owner-supplied signing secrets and a pinned certificate; helpers never create an app keystore or overwrite existing owner files. Private generated files are permission-restricted, certificate-checked and cleaned; environment reviewers/protected deployment branches must be configured by the owner. Internal signed artifacts do not imply production readiness. Inspect actual APK signatures/package/API/known secret formats and AAB per-entry JDK signatures; AAB manifest metadata still needs official bundletool and device installation is a separate gate.

Known-secret scans and source review are bounded evidence. No crash-reporting provider or additional telemetry was enabled without configuration. Preserve private build/heap/signing material and avoid raw provider/message/token logs. [Current assessment and release gates](PHASE6_RELEASE.md), [store disclosure limits](STORE_REVIEW.md). Live policy review, hosted services, actual app artifacts and device certification remain blocked.

## Phase 7 activation boundary

Owner-reported preview APK static checks/installation supersede the older lack-of-artifact checkpoint, but do not certify hosted RLS, Auth, notifications or calling. Current local SQL/security regressions pass. No target was selected or remote mutation performed. Remote migrations require explicit confirmation after target/schema/history/diff review; scheduled cleanup/push also requires target, Vault and cost review. A new public-config guard rejects a legacy anon JWT project-ref mismatch against a standard Supabase host; it does not verify JWT signatures or opaque publishable keys. Existing E2EE remains disabled. [Current evidence](PHASE7_ACTIVATION.md).
